# ระบบติดตามกิจกรรมจัดซื้อของ Buyer

ระบบติดตามกิจกรรมการจัดซื้อจัดจ้าง CAPEX / OPEX บน **Google Apps Script + Google Sheets**
Buyer เปิดงาน บันทึกสิ่งที่ทำจริงลง timeline แล้วปิดงานด้วย **เลข PR ที่ออกจากระบบ EPICOR**
พร้อมระบุว่าบริษัทใดในเครือเป็นผู้จัดซื้อ

---

## 1. สิ่งที่ระบบทำได้

| ความสามารถ | รายละเอียด |
|---|---|
| เปิด Case | ออกเลข `SRC-YYYY-0001` อัตโนมัติ พร้อมสร้างโฟลเดอร์ใน Google Drive ให้ทันที |
| บันทึกกิจกรรม | timeline ของสิ่งที่ Buyer ทำจริง พร้อม "สิ่งที่ต้องทำต่อ" และวันครบกำหนด (ใส่หรือไม่ใส่ก็ได้) |
| ปิดงานด้วยเลข PR | บังคับกรอกเลข PR จาก EPICOR และบริษัทที่จัดซื้อ — เขียนพร้อมกับการเปลี่ยนสถานะในครั้งเดียว |
| กันเลข PR ซ้ำ | เลข PR หนึ่งเลขปิดงานได้ใบเดียว ถ้าซ้ำระบบบล็อกและบอกว่าไปอยู่ที่งานไหน |
| ทะเบียนผู้ขาย | ค้นหา เพิ่ม แก้ไข ตรวจซ้ำ Tax_ID และเตือนเมื่อเบอร์/อีเมล/ที่อยู่ตรงกับผู้ขายรายอื่น |
| ย้อนสถานะอัตโนมัติ | ถ้าเลข PR ของงานที่ปิดแล้วหายไป ระบบเปิดงานกลับเอง บันทึก log และส่งอีเมลแจ้ง |
| ประวัติการแก้ไข | Change_Log ระดับฟิลด์ เพิ่มได้อย่างเดียว ลบหรือแก้ไม่ได้ |
| ภาพรวมทีม | หัวหน้า/ผู้ตรวจสอบเห็นภาระงานรายคน งานที่เลยกำหนด และงานที่พร้อมปิด |
| อีเมลแจ้งเตือน | สรุปรายวันฉบับเดียวต่อคน + แจ้งทันทีเมื่อโอนงานและเมื่อระบบย้อนสถานะ |

**ยังไม่อยู่ในขอบเขต:** การหา Vendor และเปรียบเทียบราคาในระบบนี้ (ทำใน EPICOR), เลข PO / GR, Dashboard บน Looker Studio

## 2. วงจรของงาน

```
                 ┌─────────────┐
   เปิด Case  →  │   เปิดงาน   │ ──────────────┐
                 │    OPEN     │               │
                 └──────┬──────┘               ▼
                        │                ┌───────────┐
       บันทึกกิจกรรมระหว่างทาง            │  ยกเลิก   │
                        │                │ CANCELLED │
       ปิดงาน + เลข PR + บริษัท          └───────────┘
                        ▼
                 ┌─────────────┐
                 │   ปิดงาน    │   ← Reopen ได้โดยหัวหน้าฝ่ายจัดซื้อเท่านั้น
                 │   CLOSED    │
                 └─────────────┘
```

**เงื่อนไขเดียวที่ระบบบังคับก่อนปิดงาน**

1. มีเลข PR จากระบบ EPICOR
2. เลข PR นั้นยังไม่ถูกใช้ปิดงานอื่น
3. ระบุบริษัทที่จัดซื้อ และต้องเป็นรหัสที่อยู่ในชีต `Config_Lists` (`List_Name = COMPANY`)

ทั้งสามข้อถูกตรวจที่ `Rules.evaluate()` ที่เดียว ซึ่งเป็นตัวเดียวกับที่ป้ายบนหน้ารายการงาน
แถบเตือนบนหน้ารายละเอียดงาน และตัวกันการเปลี่ยนสถานะใช้ร่วมกัน

## 3. โครงสร้าง `src/` แปลงเป็นอะไรใน Apps Script

**Apps Script ไม่มีโฟลเดอร์** โฟลเดอร์ใน repo นี้มีไว้ให้คนอ่านโค้ด — ตอน `clasp push`
clasp จะเอา path มาเป็น *ชื่อไฟล์* ที่มี `/` อยู่ในชื่อ (ตัดเฉพาะนามสกุลสุดท้ายออก)

| บนดิสก์ | ชื่อไฟล์ใน Apps Script | ชนิด |
|---|---|---|
| `src/server/Auth.js` | `server/Auth` | `.gs` |
| `src/client/Index.html` | `client/Index` | `.html` |
| `src/client/App.js.html` | `client/App.js` | `.html` (ตั้งชื่อแบบนี้เพื่อให้ editor ไฮไลต์ JS) |
| `src/client/views/MyCases.html` | `client/views/MyCases` | `.html` |

สองอย่างที่ตามมา:

- **ไฟล์ `.gs` ทุกไฟล์ใช้ global scope ร่วมกัน** ไม่ว่าจะอยู่ "โฟลเดอร์" ไหน `Api.js` จึงเรียก
  `CaseService.create()` ได้โดยไม่ต้อง import — และเป็นเหตุผลที่ test harness โหลดทุกไฟล์เข้า
  vm context เดียวกัน
- **ไฟล์ `.html` ต้องอ้างด้วยชื่อเต็ม** เช่น `include('client/views/MyCases')`

### ⚠️ กับดัก: `rootDir` ต้องไม่หาย

บรรทัด `"rootDir": "src"` ใน `.clasp.json` คือสิ่งที่ทำให้ `src` ไม่ติดมาในชื่อไฟล์
`clasp create` จะเขียน `.clasp.json` ใหม่ทับ — ถ้า `rootDir` หลุดไป ชื่อไฟล์จะกลายเป็น
`src/server/Auth` และ `src/client/Index`

repo นี้มี `.clasp.json` อยู่แล้ว `clasp create` จึงจะ **refuse** (`Project file already exists`)
ซึ่งเป็นเรื่องดี — ให้สร้างโปรเจกต์จากหน้าเว็บแล้วแก้เฉพาะ `scriptId` ตามขั้นตอนข้างล่าง

> ระบบทนต่อกรณีนี้อยู่แล้ว (`resolveHtmlName()` ใน `Main.js` จะไล่ลองชื่อสำรองให้)
> แต่ `verifyDeployment()` จะขึ้นคำเตือนเพื่อให้กลับไปแก้ config ให้ถูก

## 4. การติดตั้งครั้งแรก

> 📘 **ติดตั้งครั้งแรกให้เปิด [`docs/INSTALL.md`](docs/INSTALL.md) ตามทีละขั้น**
> หัวข้อนี้เป็นเวอร์ชันย่อสำหรับคนที่ใช้ clasp อยู่แล้ว

**สร้างเป็น standalone script เท่านั้น** — ไปที่ [script.google.com](https://script.google.com) → `New project`
**อย่า**สร้างจากเมนู `Extensions` → `Apps Script` ในชีต (นั่นคือ container-bound: ลบชีตแล้วสคริปต์หายไปด้วย
และเปลี่ยน DB ทีหลังไม่ได้)

ชีตที่เก็บข้อมูลเป็นคนละไฟล์กับสคริปต์ และ **`setup()` สร้างให้เอง** — ไม่ต้องสร้างชีตไว้ก่อน

```bash
clasp login

# สร้างโปรเจกต์เปล่าที่ https://script.google.com → New project
# คัดลอก Script ID จาก Project Settings มาใส่ .clasp.json — อย่าแตะ rootDir

clasp push      # 33 ไฟล์: server 23 + client 10
clasp open
```

จากนั้นในหน้าต่าง Apps Script:

1. **รัน `setup()` หนึ่งครั้ง** — สร้างไฟล์ Google Sheets ชื่อ `Buyer Procurement Activity — DB`
   ครบ 9 ชีต ใส่หัวคอลัมน์และข้อมูล Config เริ่มต้น และเพิ่มบัญชีที่รันลงชีต `Users` เป็น `ADMIN`
2. **เปิดไฟล์ DB แล้วเพิ่มบริษัทในเครือ** ในชีต `Config_Lists` (`List_Name = COMPANY`)
   ค่าที่ให้มามีแค่ `PLANB` หนึ่งแถวเป็นตัวอย่าง
3. **เพิ่มผู้ใช้ในชีต `Users`**
4. **รัน `installTriggers()` หนึ่งครั้ง** เพื่อตั้งอีเมลแจ้งเตือนรายวัน
5. **Deploy เป็น Web app** — `Execute as: Me` และ `Who has access: Anyone within (โดเมนบริษัท)`
6. **รัน `verifyDeployment()`** แล้วอ่าน Execution log — จะได้ checklist บอกว่ามีอะไรยังไม่เรียบร้อย

> ⚠️ **ห้ามแชร์ไฟล์ DB ให้ผู้ใช้ทั่วไป** ระบบถูกออกแบบให้ผู้ใช้เข้าถึงข้อมูลผ่านหน้าเว็บเท่านั้น

ทุกครั้งที่แก้โค้ดแล้ว `clasp push` ต้อง `Deploy` → `Manage deployments` → แก้ deployment เดิมเป็น
`New version` ด้วย ผู้ใช้จึงจะเห็นของใหม่

## 5. การตั้งค่า (ชีต `Config_Settings`)

| Key | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `BUYER_CAN_VIEW_ALL` | `TRUE` | Buyer เห็นงานของคนอื่นแบบอ่านอย่างเดียว |
| `DRIVE_ROOT_FOLDER_ID` | (ว่าง) | โฟลเดอร์หลักที่เก็บโฟลเดอร์ของแต่ละงาน — ถ้าเว้นว่าง ระบบจะสร้างให้ครั้งแรกที่ใช้งานแล้วเขียนค่ากลับมาที่นี่ |
| `REMINDER_HOUR` | `8` | ชั่วโมงที่ส่งอีเมลสรุปรายวัน (ต้องรัน `installTriggers()` ใหม่หลังแก้) |
| `REMINDER_DAYS_AHEAD` | `1` | เตือนสิ่งที่ต้องทำต่อที่ครบกำหนดภายในกี่วันข้างหน้า |
| `APP_TIMEZONE` | `Asia/Bangkok` | โซนเวลาของระบบ |

**ชีต `Config_Lists`** เก็บทุก dropdown ในระบบ (`List_Name`, `Code`, `Label_TH`, `Parent_Code`, `Sort_Order`, `Is_Active`)

| List_Name | ใช้ที่ไหน |
|---|---|
| `COMPANY` | **บริษัทที่จัดซื้อ ตอนปิดงาน** — ใส่ Planbmedia และบริษัทในเครือทั้งหมดที่นี่ |
| `DEPARTMENT` | หน่วยงานที่ขอซื้อ (ค่าที่ให้มาเป็นตัวอย่าง) |
| `BUDGET_TYPE` / `SUB_TYPE` | ประเภทงบและประเภทย่อย — `SUB_TYPE` ใช้ `Parent_Code` เป็น `Budget_Type` |
| `METHOD` | วิธีจัดซื้อ |
| `ACTIVITY_TYPE` | ประเภทกิจกรรมใน timeline — `Parent_Code` เป็นรหัสโมดูล (`M1`) |
| `CHANNEL` | ช่องทางที่ติดต่อ (โทร / อีเมล / LINE / ประชุม / ลงพื้นที่) |
| `VENDOR_STATUS` · `ROLE` | สถานะผู้ขาย และบทบาทผู้ใช้ |

**ทุกรายการในตารางนี้ผู้ดูแลระบบแก้เองได้ในชีต ไม่ต้องแก้โค้ด** — เพิ่มแถวใหม่ทำได้เสมอ
(`Sort_Order` คุมลำดับใน dropdown) ส่วนการแก้ของเดิมมีข้อควรระวัง 3 ข้อ

| แก้อะไร | ผลที่ตามมา |
|---|---|
| `Label_TH` | **ปลอดภัยเสมอ** ชื่อที่แสดงเปลี่ยนทันที ทั้งข้อมูลเก่าและใหม่ |
| `Code` | **ห้ามแก้หลังมีข้อมูลใช้ไปแล้ว** ข้อมูลเก่ายังเก็บรหัสเดิม พอหารหัสนั้นไม่เจอ หน้าจอจะแสดงรหัสดิบแทนชื่อไทย เช่น `EMAIL_RFQ` |
| `Is_Active = FALSE` | ซ่อนออกจาก dropdown แต่**ข้อมูลเก่าที่ใช้รหัสนั้นจะแก้ไขไม่ได้** (ระบบตรวจกับรายการที่เปิดใช้อยู่เท่านั้น) — ถ้ายังต้องแก้ของเก่า ให้เปิดกลับชั่วคราว |

**ห้ามลบแถวทิ้ง** ใช้ `Is_Active = FALSE` แทนเสมอ

> หลังแก้ชีต Config ให้ผู้ดูแลระบบกดล้าง cache (`api_clearCache` ผ่านผู้ใช้บทบาท ADMIN)
> หรือรอไม่เกิน 10 นาที

หากต้องการให้เฉพาะหัวหน้าปิดงาน แก้ `canCloseCase` ใน `Auth.permissions()` บรรทัดเดียว

## 7. กฎอื่นที่ระบบบังคับ

**ต้องระบุเหตุผลเสมอเมื่อ** ลบข้อมูลใดๆ, ยกเลิกงาน, โอนงาน และ Reopen

**การตรวจข้อมูลซ้ำ**

| กรณี | ผลลัพธ์ |
|---|---|
| เลข PR ซ้ำกับงานอื่น | **บล็อก** พร้อมบอกว่าเป็นงานไหน |
| Tax_ID ซ้ำในทะเบียนผู้ขาย | **บล็อก** พร้อมบอกว่าเป็นผู้ขายรายใด |
| เบอร์โทร / อีเมล / ที่อยู่ ตรงกับผู้ขายรายอื่น | **เตือน** แต่บันทึกได้ |
| เปิดงานใหม่ที่เอกสารอ้างอิงซ้ำกับงานที่ยังเปิดอยู่ | **เตือน** |

**การแก้ไขพร้อมกัน** — ทุกการบันทึกส่งเลขเวอร์ชันของข้อมูลกลับมาด้วย ถ้าไม่ตรงกับในชีต
ระบบจะตอบ `CONFLICT` และไม่เขียนทับงานของคนที่บันทึกไปก่อน

**งานที่ปิดแล้วถูกแช่แข็ง** — แก้ไขข้อมูล บันทึกกิจกรรม หรือเปลี่ยนสถานะไม่ได้
จนกว่าหัวหน้าฝ่ายจัดซื้อจะกด Reopen พร้อมระบุเหตุผล

## 8. การทดสอบ

ชุดทดสอบไฟล์เดียว (`tests/Tests.js`) รันได้สองที่

```bash
npm test                        # รันทั้งหมดบน Node (ไม่ต้องมีบัญชี Google)
node tests/node/run.js --grep close
npm run check                   # ตรวจ syntax ทุกไฟล์ใน src/server
```

`tests/node/run.js` โหลดไฟล์ทุกไฟล์ใน `src/server` เข้า **vm context เดียวกัน** ซึ่งเลียนแบบ
global scope ของ Apps Script ตรงๆ โค้ดที่ถูกทดสอบจึงเป็นโค้ดชุดเดียวกับที่ deploy จริง
โดยไม่ต้องมี `require`/`module.exports` ในโค้ดฝั่ง server เลย

ตัวรันจงใจโหลดไฟล์ **เรียงตามตัวอักษร** ซึ่งเป็นลำดับที่แย่ที่สุดที่โค้ดชุดนี้น่าจะเจอบน Apps Script
(`Rules.js` มาก่อน `StatusEngine.js`, `Api.js` มาก่อนทุกอย่างที่มันเรียก) โมดูลที่เผลอเรียกโมดูลอื่น
ตอนโหลดไฟล์จึงพังในเทสต์ แทนที่จะไปพังบน production ที่มันจะทำให้ทั้งสคริปต์โหลดไม่ผ่าน

**ทดสอบบน Google จริง** — หลัง `clasp push` ให้รัน `verifyDeployment()` ก่อน แล้วตามด้วย `runAllTests()`
จาก Apps Script editor เพื่อยืนยันสิ่งที่ mock ตรวจแทนไม่ได้ (quota, การ escape ของ HtmlService,
สิทธิ์ Drive, การส่งอีเมลจริง) การทดสอบจะสร้างไฟล์ Google Sheets ชั่วคราวสำหรับแต่ละเคสแล้วย้ายลงถังขยะให้เอง

จากนั้นทดลองใช้กับงานจริงตาม [`docs/UAT.md`](docs/UAT.md) ก่อนเปิดให้ทั้งฝ่ายใช้

## 9. การสำรองข้อมูล

ข้อมูลทั้งหมดอยู่ในไฟล์ Google Sheets ไฟล์เดียว

- **อัตโนมัติ** — Google Sheets เก็บ version history ย้อนหลังให้อยู่แล้ว (`File` → `Version history`)
- **รายเดือน (แนะนำ)** — `File` → `Make a copy` เก็บไว้ในโฟลเดอร์สำรอง หรือดาวน์โหลดเป็น `.xlsx`
- **ก่อนแก้ Schema ครั้งใหญ่** — สำเนาไฟล์ DB ไว้ก่อนรัน `setup()` ทุกครั้ง
- **ห้ามใส่สูตรในชีต DB** ระบบอ่านค่าดิบเท่านั้น
- **ห้ามลบแถว** ระบบใช้ soft delete (`Is_Deleted = TRUE`) ทั้งหมด การลบแถวจริงจะทำให้ประวัติขาด

> แก้เลข PR ตรงในชีตแล้วลบทิ้ง จะทำให้ระบบเปิดงานนั้นกลับเป็น `OPEN` เองในงานรายวันถัดไป
> พร้อมบันทึก log ในชื่อ `SYSTEM` และส่งอีเมลแจ้งเจ้าของงาน — นี่คือพฤติกรรมที่ตั้งใจไว้

## 10. PDPA — ข้อมูลส่วนบุคคล

ชีต `Vendors` เก็บ `Contact_Name`, `Contact_Phone`, `Contact_Email` และ `Address` ซึ่งเป็น
**ข้อมูลส่วนบุคคล** เก็บไว้เพื่อวัตถุประสงค์การจัดซื้อจัดจ้างเท่านั้น ระบบจึง:

- ไม่ส่งข้อมูลผู้ติดต่อออกไปในอีเมลแจ้งเตือนใดๆ (มีชุดทดสอบตรวจข้อนี้โดยเฉพาะ)
- ไม่แชร์ไฟล์ DB ให้ผู้ใช้ทั่วไป — เข้าถึงได้ผ่านหน้าเว็บที่ตรวจสิทธิ์แล้วเท่านั้น
- ตั้งค่าแชร์ไฟล์แนบใน Drive ให้เห็นได้เฉพาะภายในโดเมนของบริษัท

ผู้ดูแลระบบควรทบทวนรายชื่อในชีต `Users` เป็นระยะ และตั้ง `Is_Active = FALSE` สำหรับผู้ที่ไม่ได้ทำงานแล้ว

  Bootstrap.js      จุดเดียวที่ประกอบโมดูลเข้าด้วยกัน (เรียกตอน runtime)

### หลักการที่ยึดตลอด

1. **Case เป็นแกนกลาง** — ทุกอย่างผูกด้วย `Case_ID` ที่ระบบออกเอง ไม่ใช้เลข PR เป็นตัวตั้ง
   เพราะ PR เกิดขึ้นหลังงานเดินไปแล้ว ไม่ใช่ตอนเริ่ม
2. **การปิดงานเป็นการตัดสินใจเดียว ไม่ใช่สองขั้นตอน** — เลข PR, บริษัท และสถานะถูกเขียนใน
   `Repository.update()` ครั้งเดียว งานจึงไม่มีทางอยู่ในสภาพ "ปิดแล้วแต่ไม่มีเลข PR"
3. **ไม่เก็บค่าที่คำนวณได้**
4. **Soft delete เท่านั้น** — ไม่มีโค้ดส่วนใดลบแถวจริง
5. **อ้างอิงด้วย ID และชื่อคอลัมน์เสมอ** — ไม่ใช้เลขแถวหรือ index ตายตัว คอลัมน์ที่เพิ่มทีหลังจึงไม่ทำให้อะไรพัง
6. **ตรวจสิทธิ์ที่ server ทุกครั้ง** — การซ่อนปุ่มฝั่ง client เป็นความสะดวก ไม่ใช่การควบคุม
7. **ห้ามโมดูลเรียกหากันตอนโหลดไฟล์** — Apps Script เป็นผู้กำหนดลำดับการประมวลผลไฟล์เอง
   โค้ดที่เรียกโมดูลอื่นตอนโหลดจึงทำงานได้ด้วยความบังเอิญ และวันที่ลำดับเปลี่ยน สคริปต์จะโหลด
   ไม่ผ่านทั้งโปรเจกต์ ทุกโมดูลจึงลงทะเบียนตัวเองผ่าน `install()` ที่ `Bootstrap.js` เรียกตอน runtime

## 12. การต่อยอด

โครงสร้างถูกวางไว้ให้ "เพิ่ม" ได้โดยไม่ต้องแก้ของเดิม

| สิ่งที่ต้องทำ | วิธี |
|---|---|
| เพิ่มตารางหรือคอลัมน์ | เพิ่ม entry ใน `Schema.js` แล้วรัน `setup()` ซ้ำ — คอลัมน์ใหม่จะถูกเพิ่มต่อท้าย ข้อมูลเดิมไม่เสีย |
| เพิ่มสถานะใหม่ | เพิ่มแถวในชีต `Status_Master` แล้วใส่รหัสนั้นใน `Allowed_Next` ของสถานะที่มาก่อน |
| เพิ่มกฎก่อนเปลี่ยนสถานะ | เขียน `MyRules.install()` ที่เรียก `StatusEngine.registerRule(from, to, MyRules.check)` แล้วเพิ่มหนึ่งบรรทัดใน `Bootstrap.install()` — **อย่าเรียกตอนโหลดไฟล์** |
| เพิ่มเงื่อนไขย้อนสถานะอัตโนมัติ | `StatusEngine.registerRecheck(MyRules.recheck)` ภายใน `install()` เดียวกัน |
| เพิ่มประเภทกิจกรรม | เพิ่มแถวใน `Config_Lists` ที่ `List_Name = ACTIVITY_TYPE` |
| เพิ่มแท็บในหน้ารายละเอียดงาน | สร้างไฟล์ใน `src/client/views/` เรียก `App.registerCaseTab({...})` แล้ว `include` ใน `Index.html` และเพิ่มชื่อไฟล์ใน `Verify.HTML_FILES` |
| เพิ่มปุ่มบนหัวหน้ารายละเอียดงาน | `App.registerCaseHeaderAction({...})` |
